      - 大概：```(x',y',z') @ (x0,y0,z0)```，其中x',y',z'分别是世界坐标系xyz单位坐标在相机坐标系的表示（在相机坐标系中用相机坐标系的坐标轴来表示）

    - 换句话说，rvec 定义了相机坐标系相对于世界坐标系的姿态（orientation），但从变换的角度看，它是将世界坐标系的点变换到相机坐标系的旋转。
    - ~~遵守右手法则，右手法则的方向**弧度增大**~~

    - 需要详细学习rvec：
      - rvec的方向为旋转轴的方向，rvec的模长为旋转的弧长
      - $$
        \mathbf{n} = \frac{\mathbf{r}}{\|\mathbf{r}\|}\\
        \theta = \|\mathbf{r}\|\\
        R = \cos\theta I + (1 - \cos\theta)\mathbf{n}\mathbf{n}^T + \sin\theta [\mathbf{n}]_\times\\
        [\mathbf{n}]_\times为反对称矩阵
        $$
      
      -  "坐标系的变换主要有两种说法，一种是主动一种是被动，而旋转向量就是一种主动变换"
    
  - Rodrigues公式之后的旋转矩阵，描述了*相机坐标系相对于世界坐标系的变换*，也就是**世界坐标系的xyz在相机坐标系中的表示**，如果用公式来看就是```Pc = R @ Pw + tvec```
  
    - 其三个列向量的分量分别代表着世界坐标系的xyz轴在相机坐标系的表示
    - 由于正对标定板时旋转矩阵近似对角阵，可以判断：世界坐标系的xyz轴与正对标定板时相机坐标系的xyz轴一致
    - 而我们知道opencv中约定俗称的相机坐标系，可以判断“opencv眼里的”世界坐标系为：标定板右x，下y，前-z
    - 此时使用公式```-R.T @ tvec```得到的t已经在opencv眼里的世界坐标系表示正确

              t = -R.T @ tvec.flatten()
              pose_pyrender,camera_pose = np.eye(4),np.eye(4)
              T_opencv2pyrender = np.array([[1,0,0],[0,-1,0],[0,0,-1]])
              pose_pyrender[:3,:3] = T_opencv2pyrender @ R.T @ T_opencv2pyrender
              pose_pyrender[:3,3] = T_opencv2pyrender @ t
              camera_pose[:3,:3] = T_opencv2pyrender @ R @ T_opencv2pyrender
              camera_pose[:3,3] = T_opencv2pyrender @ t
              #print(pose_pyrender,camera_pose)
            
              return pose_pyrender,camera_pose
      ``````

- 相机的数据读取

  - ```cv2.VideoCapture(file)```这个函数中file可以是一个视频文件，同样也可以是一个设备标识符（这又回到了Linux中一切皆文件的哲学）
  - ```ret,frame = cap.read()```reutrn值（是否读取成功）与一帧的（unint8）BGR数据
    - 关于这个现象的一个简单解释是：早期某些硬件的限制，（RGB理应在数据后段存储，表现为0x00BBGGRR）内部数据是小端存储，变成0xRRGGBB00
    - 因此现在我们知道RGB与BGR仅仅只是在存储的方向上有区别，使用```[:,:,::-1]```对于所有的点，的BGR值从后往前迭代并创建新的数组。

###### 代码风格：OOP面向对象架构

* 应用OOP的原则：
  * python的面向对象是和c++一致的
  * 封装Encapsulation（私有的属性：以_，__开头）限制外部访问
  * 继承，复用代码
  * 多态，不同类的对象通过相同接口调用方法
  * 抽象，使用抽象基类隐藏实现的细节，只暴露必要的接口
* SOLID原则
  * 单一责任原则 Single Responsibility Priciple SRP
  * 开闭原则 Open-Closed Priciple OCP 类对扩展开放对修改关闭
  * 里氏替换 Liskov Substitution LSP 子类必须能替换父类二不影响程序的正确性
  * 接口隔离原则 Interface Segregation ISP 客户端不应该依赖不需要的接口
  * 依赖倒置原则 Dependency Inversion DIP 高层模块不应该依赖底层模块
* 设计模式：
  * 创建：例如工厂模式，用于创建对象
  * 结构型模式：适配器Adapter用于兼容不兼容的接口
  * 行为型模式：例如观察者Obeserver 用于事件通知，Strategy用于算法切换
* 实践：
  * 保持类小而专注，一个文件一个类，方法不超过20-30行
  * 优先组合而非继承
  * 利用属性 Properties为getter/setter提供简洁的接口
  * typing 模块添加类型注解提高可读性
  * 测试驱动开发TDD，设计前写单元测试确保架构robust
  * 避免全局变量来保存状态
  * 模块化，相关类分组到包中，使用```__init__.py```组织

* 现有问题：
  * ImageGenerator承担太多责任，相机初始化、渲染、轴视图生成、线程管理等），违反了单一责任原则（SRP）
  * MainWindow类也混在了GUI布局和图像更新的逻辑
* GROK建议：抽象6个核心类
  * Config类
  * Camera类
  * Renderer类
